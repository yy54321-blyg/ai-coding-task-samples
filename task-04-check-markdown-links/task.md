# Task 04 · 检查 Markdown 文件中的外部链接是否失效

## 需求

扫描一个 `.md` 文件（或目录下的全部 `.md`），提取所有链接并检查其有效性，输出死链报告。

**提取规则：**

1. 匹配 `[文本](url)` 和 `![alt](url)`
2. **排除**：`#锚点`、`mailto:`、`tel:`、以及所有**不以 `http` 开头的相对路径**
3. 同一 URL 只检查一次（去重）

**检查规则：**

1. 先发 `HEAD` 请求；若返回 `403` / `405` / `501`，**回退为 `GET`** 再判断
2. 超时 5 秒
3. 状态码 `2xx` / `3xx` 视为有效；其余视为死链
4. 请求异常（DNS 失败、超时、SSL 错误）记为死链，`status` 填 `ERR`
5. **并发检查**，不要串行等待

**输出：** `dead-links.csv`，列为 `file,line,url,status,error`

---

## 输入示例

`docs/a.md`

```markdown
# 标题
见 [Python 官网](https://www.python.org)。
图片 ![logo](./images/logo.png)
锚点 [跳到第二节](#第二节)
邮箱 [联系](mailto:a@b.com)
坏链 [不存在](https://example.com/definitely-not-exist-12345)
```

## 期望输出

`dead-links.csv`

```csv
file,line,url,status,error
docs/a.md,5,https://example.com/definitely-not-exist-12345,404,
```

> 相对路径 `./images/logo.png`、锚点 `#第二节`、`mailto:` **不应出现在结果里**。

---

## 验收标准（可测）

- [ ] 相对路径、`#锚点`、`mailto:`、`tel:` **均不进入检查流程**
- [ ] 图片链接 `![]()` 也能被提取（不是被跳过）
- [ ] `404` 链接被列入结果，`200` 链接不出现
- [ ] 对返回 `405` 的 URL，**回退 `GET` 后判定为有效**，不误报
- [ ] 请求超时 5 秒后放弃，**不阻塞整个流程**
- [ ] 20 个不同 URL 的检查总耗时应显著小于串行的 20 × 5 秒
- [ ] 连接失败时 `status=ERR`、`error` 记录异常类型，脚本不崩溃
- [ ] 输出中同一 URL 不重复出现
- [ ] 输出文件包含 `line` 字段，能定位到具体行号

## 难度

**中等偏高**

涉及能力：
- 正则提取（需要处理 URL 中含 `?`、`&`、`%` 的情况）
- HTTP 语义（`HEAD` 与 `GET` 的差异、重定向、状态码分类）
- 并发编程（线程池）
- 超时与异常处理
- 去重与结果聚合

## 常见错误（AI 典型失败模式）

| # | 错误 | 正确做法 |
|---|---|---|
| 1 | 只发 `HEAD` → 大量站点返回 `403/405`，**误报成死链** | 遇到 `403/405/501` 回退 `GET` |
| 2 | **串行 `requests.get`** → 100 个链接要等十几分钟 | `ThreadPoolExecutor` 并发 |
| 3 | 不设 `timeout` → 单个死链卡住整个程序 | 每个请求显式传 `timeout=5` |
| 4 | 把 `#锚点`、相对路径当外链去请求 → 全是 `ERR` | 先过滤 `http(s)://` 前缀 |
| 5 | 正则写成 `\[(.*)\]\((.*)\)` → 贪婪匹配跨行 | 用 `[^\]]` / `[^)\s]+` 限制字符集 |
| 6 | 把图片 `![]()` 漏掉（只匹配 `[]()`） | 正则前缀写 `!?` |
| 7 | 同一 URL 在不同文件出现，重复请求几十次 | 先全局去重，再并发检查 |
| 8 | 未处理重定向，把 `301` 当无效 | `allow_redirects=True` |
| 9 | URL 中含 `(` `)` 时被截断（如维基百科链接） | **需在题目中声明局限**，或改用 `[^)\s]+` + 平衡括号处理 |

## 已知边界（题目设计说明）

URL 内含**成对括号**（如 `https://en.wikipedia.org/wiki/Python_(programming_language)`）时，
简单正则会截断。本任务明确**接受该局限**，并要求实现者在 `README` 中说明——

> **能识别出"需求本身的边界"，比默默做错更符合"任务设计"的要求。**
> 这也是我把这一条写进验收说明、而不是写进代码的原因。

## 为什么这个任务适合评测

- **有多个"看起来对但实际错"的实现**：只发 HEAD、串行请求、误判锚点
- **失败方式可测且明显**：误报率、耗时、漏检率
- **需要工程判断**：并发/超时/重试/去重的取舍
- **真实高频需求**：文档维护、站点巡检
